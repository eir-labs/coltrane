# Audit — `coltrane-oss` current state + gaps

**Auditor:** miles (grid-diamondcutter bandleader lane, per Eugene's
request at 12:36 CEST 2026-05-29)
**Audit scope:** ship-readiness for public release as an Apache-2.0
agent-orchestration MCP server.
**Audit method:** repo survey + verify-gate run + cross-reference with
`Coltrane Spec.docx.md`, `prereg.md`, `docs/CURRENT_STATE_2026-05-26.md`,
and `tracking.json`. Compared against grid-diamondcutter's publication-
window audit pattern (phase-A + phase-2 closed earlier today).

This document is honest, not promotional. The "odd process over there
with no commits" Eugene flagged at 12:35 CEST is itself one of the
audit's findings — the single-`Initial commit` history affects the
ship-readiness assessment.

## TL;DR

`coltrane-oss` is **engineering-complete and verify-green** at the
deterministic-suite scope. It is **NOT yet ship-ready as a public OSS
release** in the way grid-diamondcutter's phase-A reached
ship-readiness this morning.

Three gap classes block public ship:

1. **Process gaps** (single-commit history; no PR audit trail; no live
   `npm run verify` run on a github CI surface against actual PRs).
2. **Content gaps** (§10 company context + §11 product-development
   coverage incomplete per `tracking.json`).
3. **Live-cognition gap** (the `claude` spawn validation that exercises
   the engine end-to-end against real model output is an explicit
   manual-gate per `.github/workflows/ci.yml` — not yet exercised).

None of these are engine-correctness gaps. The engine is **sound and
green**. The gaps are about **discipline-in-action evidence** of the
kind grid-diamondcutter produced during its publication-window run.

## Gaps — process

### 1. Single-`Initial commit` history

**Observed:** `git log --oneline` returns `93f5d73 Initial commit`.
There is no per-feature commit history. The repo's authoring
provenance is invisible to a future contributor.

**Impact for ship-readiness:**

- No PR review trail. Contributors arriving at the repo cannot see
  how decisions were made.
- No incremental-verify record. Every test was apparently green at
  the single commit; there is no record of which test was added when,
  which red-then-green moment proved an invariant, or which apoha
  fired during development.
- No §5-style correction-protocol record (the kind grid-diamondcutter
  produced live during its phase-A NOAA v1→v2 unit-bug fix — two
  voices catching the same error, v1 stays on record with
  analyst-error noted, v2 ships separately).

**Comparison to grid-diamondcutter publication-window pattern:**
grid-DC shipped 99 PRs across phase-A + phase-2, with each PR
carrying a verifiable predict-vs-observed ledger. The audit trail
**IS** the publication. coltrane-oss reaching a similar audit-trail
posture would require either (a) a synthetic backfill of PRs from
the existing history (risky — fabricates a non-existing review
trail), or (b) accepting the single-commit history as a known limit
and explicitly stating it on first public release with a v0→v1
discipline ratchet for all subsequent commits.

**Recommendation:** (b). Document the single-commit anomaly honestly
in a `docs/AUDIT_PUBLISH_NOTE.md` shipped at first public release;
commit to per-PR discipline from v0 onward.

### 2. No public github surface yet

**Observed:** repo is on local `master`. No public github URL
referenced in README's `git clone <repo-url>` install block.

**Impact:** the README's install instructions cannot be followed by
an external contributor today. CI workflow exists but has nothing
to run against.

**Recommendation:** create the public github repo, push the single
commit, immediately open a PR with this audit document + the
`docs/AUDIT_PUBLISH_NOTE.md` from gap (1), let CI fire on the PR to
prove the verify-gate is real on github runners, then merge to
establish per-PR discipline from PR #2 onward.

### 3. No public release tag or version anchor

**Observed:** `package.json` has `"version": "0.1.0"` but no git tag,
no release notes, no CHANGELOG.

**Recommendation:** tag `v0.1.0` at the initial-commit hash on first
public push. Add `CHANGELOG.md` at repo root. Use the v0.1.0 → v0.2.0
transition for the first multi-PR cycle (e.g., addressing gap class 2
content, or shipping the live-Claude spawn validation).

## Gaps — content

### 4. §10 company context — not covered

**Observed in `tracking.json`:** `§10 company context` assigned to
`trane`, no test files listed under that section. Per
`docs/CURRENT_STATE_2026-05-26.md`, §10 is one of the two remaining
domain lanes before public release.

**Impact:** the engine ships without a worked example of how a
deploying institution declares its charter / north-star / accountability
binding. The README mentions charter; the spec mandates the structure;
but there is no end-to-end example of charter use in the genome.

**Recommendation:** Add a charter example to `examples/` showing a
worked deploying-institution charter; add at least one test that
exercises `charter_read` → `charter_suggest_update` against the
worked example. Estimated: 1-2 days for trane lane.

### 5. §11 product-development domain — not covered

**Observed:** assigned to `lighthouse` in `tracking.json`. Same
status as §10.

**Impact:** missing end-to-end example of the product-development
schema lighthouse documented. The `eir_document_schemas.json` exists
at repo root but has no exercising voice / agent.

**Recommendation:** Add a product-development worked example showing
how `eir_document_schemas.json` integrates with the agent loop.
Estimated: 1-2 days for lighthouse lane.

### 6. README's three published hashes — verify on push

**Observed:** README lists 3 hex hashes claimed to reproduce on every
implementation. Local verify-gate green; cross-language conformance
documented in `~/eir/math/proofs/test_coltrane_canonical_form.py`.

**Concern:** if any pre-push change to the hello-skill reference,
canonical_form pipeline, or definition hash logic shifts a single
byte, the published hashes drift. This is the kind of bug that
would be caught only after a contributor tries to verify and
files an issue.

**Recommendation:** Add a `tests/published_hashes.test.ts` that
asserts the three README hashes byte-for-byte. CI fails before
publication if the hashes drift. (This may already be inside
`tests/canonical_form.test.ts` per the prereg O1 row; spot-verify.)

## Gaps — live-cognition

### 7. Live-Claude spawn gate — not yet exercised

**Observed in `.github/workflows/ci.yml`:** the live-Claude spawn is
explicitly **NOT** run in CI by design (needs CLI + key). Per
`tests/claude_invoker.test.ts` and the O14 prereg row, the pure
pieces (buildPrompt, extractJson) are tested; the spawn itself is
a non-deterministic seam intentionally excluded from unit tests.

**Concern:** the engine has not been validated end-to-end against
real model output. Pure-pieces tests pass; the integrated cognition
loop is unproven on a real Claude execution.

**Recommendation:** Eugene (or a designated band member) runs the
live-cognition gate once locally before first public release:
- `export ANTHROPIC_API_KEY=...`
- `npm run build`
- start the MCP server
- dispatch a gig with the `hello-skill` reference using a real
  Claude Code session as the cognition layer
- verify that a signed sidecar lands in the ledger end-to-end
- document the run in `docs/LIVE_COGNITION_BOOT_2026_XX_XX.md`

This is a one-time gate; doesn't need ongoing CI. But shipping
without exercising it once means the engine's central claim
(reconstructible hash-sealed record from a real cognition loop) is
untested at the integration layer.

## Risks

- **Reputation risk on first public release**: shipping with a single
  initial commit + the "we followed an odd process" backstory may
  read to outside contributors as either careless or untrustworthy.
  Mitigate via the `docs/AUDIT_PUBLISH_NOTE.md` documenting the
  process honestly + per-PR discipline from v0.1.0+ onward.

- **Live-cognition risk**: the engine has not been integration-tested
  against real Claude output. Pure-pieces tests pass; spawn is unproven.
  Mitigate via the one-time live-cognition gate before first
  public push.

- **Boundary-drift risk**: per the grid-diamondcutter / coltrane-oss
  conversation in `#e` at 12:30-12:40 CEST, the two projects are
  considering an explicit §13 boundary (grid-DC method ≠ silently
  coupled to coltrane internals). Without the §13 boundary documented
  + mechanically defended **in both repos**, future commits could
  silently couple. Mitigate via the cross-repo bridge document
  (grid-DC side in progress per cajal #PR-pending).

- **Genome-loading regression risk**: if a future commit accidentally
  hardcodes a type instead of loading it from `core_types/`,
  the rebuild-from-files litmus would fail silently unless CI runs
  the `rm -rf .coltrane-cache/ && npm run verify` cycle. Add a CI
  step that does the litmus on every PR.

## Honest reads

- **The engine itself is sound.** Verify gate green, 492 tests pass,
  cross-language conformance proven, MCP tool surface 28/32 wired.
  This is not a vapor project.

- **The project lacks audit-trail evidence.** Compared to
  grid-diamondcutter's 99 PRs in one session + per-voice
  predict-vs-observed ledger + multi-witness convergence + live §5
  correction-protocol exercise, coltrane-oss does not (yet) have
  the operational discipline-in-action evidence that grid-DC
  produced. The discipline is implicit in the test pairs but
  unwitnessed in the commit history.

- **The "odd process no commits" is fixable and not disqualifying.**
  The single-commit history is honestly documentable; per-PR
  discipline from v0.1.0+ rebuilds the trail prospectively.

- **The biggest leverage move** is auto-generating a
  `REGISTRY_STATUS.md`-analog so the test pairs become a
  publication-grade ledger visible at the repo's surface. That
  turns the implicit discipline into the explicit
  audit-defense-substrate grid-DC demonstrated.

- **First public release is reachable in days, not weeks**, at the
  band cadence grid-DC demonstrated today. The remaining work is
  evidence-of-discipline production, not engine-correctness production.
