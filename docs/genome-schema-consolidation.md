# Genome schema consolidation — one Zod source per class

## The problem (why this exists)

Every genome class's shape was restated in 3–5 hand-maintained places — the TS interface, the
construction function, the MCP `input_schema`, the handler, the file format — and they **drifted**:

- `defineAgent` returned a **hand-enumerated literal** that silently **dropped `browser_grant`** (a
  sealed field the runtime then ignored — the caged-browser bug).
- `composeStandard` **dropped** `max_examine_rounds` / `output_types` / `description` (declared in the
  JSON, gone at runtime; `max_examine_rounds` is *read nowhere* — a phantom contract).
- The MCP `agent_define` schema was **missing 8+ fields** and advertised a retired `permissions`
  object; `standard_compose` couldn't express `input_types`.
- `SkillRecord` / `EvalRecord` are `{ slug; [k]: unknown }` — **untyped bags**; the loader validates
  nothing.

Root cause: no single source of truth. Adding a field meant editing N places, and a miss drifts
silently while the seal still covers the file.

## The fix — Zod is the DNA

`src/genome_schema.ts` defines each class **once** in Zod. From the one schema we derive:

- **the type** — `z.input` (what you author) and `z.output` (after parse). Replaces the interface.
- **the validator/constructor** — `Schema.parse(def)` is loss-free: it preserves every field the
  schema declares (so `browser_grant` can never be dropped again) and applies defaults.
- **the MCP `input_schema`** — generated by `zodToMcpProps(Schema)`. The write-surface can't drift.
- **the loader's file validation** — `Schema.parse(json)` on load → a malformed/non-compliant file
  fails to enter the substrate (this is also the foundation for write-path enforcement).

zod was already a dependency, so there's no new dep.
